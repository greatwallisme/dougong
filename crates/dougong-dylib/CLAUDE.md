# CLAUDE.md — dougong-dylib

dylib/so plugin host. Trusted-code territory: the library is mapped for the whole process lifetime (D5, ruling R1 — teardown-only unloading, never `dlclose`; a reloaded plugin leaks its old image by design).

## Invariants

- Adapter ordering is contract: `setup()` → register the `teardown` effect *first* → then register bridges and `Invoker`-backed provides. LIFO makes teardown run after every bridge/provide disposer. `dougong-wasm`'s `WasmPlugin` mirrors this; keep the two in sync.
- Raw pointers cross the boundary (`Exports.table`, `Handle`). Their `unsafe impl Send/Sync` rests on the **per-instance lock** (`InstanceLock = Arc<tokio::sync::Mutex<()>>`): every foreign entry — service calls, event dispatches, deferred continuations, teardown — holds it across the call. Consumer fibers run on their own tasks and the kernel does not order cross-fiber calls, so bypassing the lock voids the safety argument.
- Cross-instance wait graph (D-V3-3, 2026-10-25 amendment): every foreign entry pushes its instance onto the held-lock chain (`LOCK_CHAIN`) after acquiring the instance lock; an acquisition arms wait edges (`WAIT_EDGES`) from every held instance and fails deterministically with `reentrancy_cycle` when the walk closes a cycle — the per-instance lock can never deadlock. Chain guards never span `.await`: the deferred waterfall continuation re-establishes its chain per poll (`ChainPoll`); the two teardown arms hold exactly one lock, so they push the chain but arm no edges. WIT has no wasm `require` import, so the graph is dylib-only — `dougong-wasm` has no counterpart to mirror.
- Event surface is ABI v2 CPS (D14): the descriptor's `listen` map (name → u32 id) drives `Context::on_dispatch` bridges. A waterfall `STATUS_DEFERRED` is followed by `next.call` and a synchronous `on_next`, all under the same lock hold — plugin state cannot observe interleaving.
- Output buffers grow on `STATUS_CAPACITY` (doubled, bounded at 16 MiB via `Exports::growable_call`) — never convert capacity into a hard failure.
- `DynPlugin` implements the kernel `Plugin` trait; the descriptor JSON (`name`/`provide`/`inject`/`listen`) drives `inject()`, the provide list, and bridge registration. The loader never overrides plugin-declared requirements.
- Runtime grants (D31 + 2026-10-28 review amendments, ABI v4): `Activation` carries its unique `instance_id` and descriptor provide set; grant records bind `(granter id, granter root id, target activation id, service)` — pure identity bookkeeping, no target Arc. `DylibInvoke::activation_id` exposes the target id and `BoundaryInvoke` forwards it, so decorator-enabled resolution stays correct. Authorization binds the *resolved provider*: `lookup_grant` returns the granter ids targeting the caller, and `require_impl` passes only when `invoker.activation_id()` is one of them (cross-realm same-name providers and stale entries stay UNDECLARED). Targets without an activation id (in-process/wasm) are rejected with `grant_target_unsupported`. Entries are root-scoped via `Context::root_id()` — cross-root requires are byte-identical UNDECLARED — and the `GRANTS_LIVE` atomic gate keeps a grant-free process's static-miss path lock-free (Release store under the insert lock pairs with the Acquire load). The global grant mutex stays a leaf (no resolution/calls/instance locks/logging inside), and `ActivationPtr::reclaim` clears grants on every normal/failed teardown arm; a hung teardown orphaned by the S3 budget leaves inert entries only (instance ids never reuse, so they can authorize nothing).
- Provider liveness gate (review F2): granted callers are not kernel dependency edges, so no drain joins them against the granter's teardown. Each activation shares an `Arc<AtomicBool>` with every `DylibInvoke` and both teardown arms; the arms clear it under the instance lock *before* the teardown export runs, and `DylibInvoke::call` checks it after `enter_exclusive` — a stale resolved invoker fails with the transport-class `provider_gone` instead of touching freed plugin state.
- `load` gates on `ABI_VERSION` from `DOUGONG_PLUGIN_EXPORTS`; a mismatch is a hard load error, not a warning.

## Tests

`cargo test -p dougong-dylib` uses static fake export tables (`from_static`) — extend them whenever `dougong-abi` changes shape. `src/outbound_tests.rs` is the ABI v3 outbound plus ABI v4 grant (E1) matrix, including decorator identity, exact two-level errors, lifecycle cleanup, concurrent grant/require, reactivation rebinding, and the 2026-10-28 review pins (E1.13 provider binding, the `provider_gone` liveness gate, E1.15 cross-root isolation, E1.16 id-less target rejection, the empty-table zero-lock gate); shared-name grant scenarios are serialized only across tests, while E1.9 retains real plugin-thread concurrency. Both test modules arm a 120s wall-clock watchdog: a synchronous FFI deadlock parks its polling thread, so no `tokio::time::timeout` can fire — the watchdog turns the wedge into a process abort (a failed suite) instead of a hang. `src/fault_tests.rs` (S7) pins the teardown failure arms: a hung teardown is orphaned by the S3 cleanup budget while the unload completes, and teardown runs exactly once under concurrent dispose (a *panicking* teardown is untestable by ABI contract — `extern "C"` exports are nounwind, so a foreign panic aborts the process; dylib is trusted code, D5). The end-to-end paths are `examples/dylib_demo.rs` (greeter showcase, incl. its ABI v3 own-thread require/emit legs) and `examples/outbound_demo.rs` (v3/v4 acceptance: full chain + grant callback against the real `grant-partner` cdylib artifact + the undeclared-capability, reentrancy-cycle and cross-instance-cycle arms — the cycle arms use embedded `from_static` tables, no extra artifact beyond the two cdylibs), both requiring `libgreeter_plugin.so` and `libgrant_partner.so` in `target/debug` (built by `cargo build --workspace`).
